# Branch guard: designs not chosen

- **A `permissions.deny` rule, with no script.** It misses `git -C`, `bash -c` and scripts, and cannot tell a worktree from the main checkout, so it would block worktrees too (research Q1).
- **An `if` filter such as `Bash(git *)` on the `settings.json` line**, as `.claude/CLAUDE.md` advises for hooks. Not chosen: an `if` uses the matching of a permission rule, which does not see `bash -c 'git ...'` (research Q9). The shell `case` on the word `git` at the start of the script keeps the cost low instead.
- **The parse in pure shell.** Not chosen: shell has no tokenizer for quotes, so `echo "git switch"` and `bash -c '...'` would be hard to read right. Python's `shlex` does it.
- **The parse in its own `.py` file.** Not chosen: the `Builds:` line names one script. The Python sits inside the shell script as `python3 -I -c`.
- **The clone root from `git rev-parse --show-toplevel`.** Not chosen: with `GIT_DIR` set from a KB, it gives the KB folder, so `GIT_DIR=<harness>/.git git branch x` would pass. The parent of the common dir is the clone root (Appendix of `1-design.md`, test 1).
- **A path test on `.claude/worktrees/` for a linked worktree.** Not chosen: R19 allows any linked worktree. The git dir against the common dir holds for each one (research Q3).
- **The first parse of this design**, which the fresh review replaced. It split on `&&`, `||`, `;` and `|` only, read `-b` only as a whole word, and kept redirects and heredoc bodies. So two lines, `&`, `-qb`, `2>/dev/null`, `git -c k=v`, `command git` and `bash -lc` each let a branch through. It also used `jq` and Python both, and a crash of the Python exited 1 with no warning.
- **The remote-only test with `for-each-ref refs/remotes/*/<name>` and `show-ref`.** Replaced in the fresh review: the pattern matches `origin/feat/x` for `feat`, and a `show-ref` error read as "no local branch", so a git error refused.
- **The remote-only test by reading `.git/refs/remotes/` on disk.** Not chosen: it misses `packed-refs`. `git for-each-ref` reads both.
- **The `settings.json` line with the git root only.** Replaced 2026-10-30 for R21: a KB worktree, another repo or an old harness worktree has no script at that root, so the hook did not run there. The line now falls back to the script of `$CLAUDE_PROJECT_DIR`.
- **The design before the second fresh review, 2026-10-30.** Replaced: comments, a backslash at a line end and joined operators such as `);` and `|&` hid a git part. A heredoc was dropped after `shlex`, so an apostrophe in it failed open. `git checkout HEAD` read `origin/HEAD` as remote-only. `git branch -v x` passed. The `cd` of a `( ... )` leaked out. `git switch -c` picked its message with no git call in the graph, and a crash had no edge. Two invariants judged any part, not the refused one.
- **The parse before the build review, 2026-10-30:** each part with words after `--` was `other`, so `git branch -- x` passed. Only `-C`, `-c`, `--git-dir`, `--work-tree` and `--namespace` took a value, a relative `GIT_DIR` resolved before `-C`, a long flag of a wrapper took no value, and a `<<` in `$((...))` started a heredoc. The Frieren review of `p-build` found five commands that passed for these, and the user picked to fix all five.
- **The raw pass before the second build review, 2026-10-30:** a `$(...)` inside double quotes was read as quotes, so an inner `"` ended the outer quote, and a quoted `git switch` in a commit message was refused. Only `$((` hid a shift, and `<<\EOF` took `\EOF` as its end word. The last Frieren review of `p-build` found these, and the user picked to fix them, then build.
- **The model before the third build review, 2026-10-30:** `judge` checked the place before the name, so a git error warned for an unreadable name, which the code passes first with no warning. The raw pass read `$'...'` as single quotes, and `subst_end` skipped no comment and no `<<<`. The user said yes to each fix.
