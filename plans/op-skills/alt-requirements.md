# Op skills: dropped and changed requirements

- **R7 and R11 before 2026-10-20: one `op-fork`.** The user runs `op-fork`. The fork runs in the same directory as the session, worktree or not. `op-fork` makes no new worktree and no new branch. Changed: a fork in the same worktree can never own it, so `worktree-end` in the fork cannot remove it. The user split the skill in two on 2026-10-20: `op-fork-keep` keeps this behavior (R7), and `op-fork-new-wt` forks into a new worktree from `main` (R23). R11 now names both. See [`closed-q.md`](#open-questions).
- **R3. Fork follows the worktree.** If the session is in a linked worktree, the fork runs in a worktree too. If not, the fork runs in the same directory as the session. Not chosen: The user wants the fork in the same worktree as the session, as in their own test, not in a new one. R7 replaces it. Research Q5 in `research/fork-session.md` compared the two options. Dropped 2026-10-18. It came back on 2026-10-20 as R23, from `main`: see `op-fork-new-wt`.
- **R6. The model checks the design only.** A Quint model holds the states and moves of `op-fork`: in a worktree or not, in cmux or not, and the result of each. The model checks the design at set points. It does not check a live run. The scripts of R5 check each run. Not chosen: after R7, `op-fork` acts the same in a worktree and outside one, so the model has no worktree state. R8 replaces it. Dropped 2026-10-18.
- **R1. Session facts.** Each skill finds the facts it needs about the session it runs in: the session ID, the directory, and whether that directory is a linked git worktree. It does not ask the user for them. Not chosen: it did not name the cmux fact that `op-fork` needs, and listed the worktree fact that only `op-code` needs. R9 replaces it, with the facts per skill. Dropped 2026-10-18.
- **R2. Fork in a new pane.** The user runs `op-fork`. A fork of the current session opens in a new cmux pane, next to the current one, and the fork keeps the whole conversation. The current session goes on as before. If the session does not run inside cmux, `op-fork` opens nothing. It says why and gives the user the command to run by hand. Not chosen: it did not say which command the user gets, or what happens when a command fails. R11 replaces it. Dropped 2026-10-18.
- **R4. Open VS Code at the root.** The user runs `op-code`. VS Code opens a window at the root of the session's worktree. If the session is not in a linked worktree, VS Code opens at the root of its git repo. If the directory is not in a git repo, `op-code` opens nothing and says so. Not chosen: it did not say what happens when a window on that folder is open already, or when `code` fails. R12 replaces it. Dropped 2026-10-18.
- **R5. Each run is checked by scripts.** Each skill has two check scripts, written before the skill. A run passes only when both pass. A state check reads the files a run writes, and reports the state the run is in. An output check tests the output of that state. `op-code` writes no file, so it has no state check. Not chosen: "each skill has two" contradicted "`op-code` has no state check", and it did not say when the checks run or what counts as output. R10 replaces it. Dropped 2026-10-18.
- **R8. The model checks the design only.** A Quint model holds the states and moves of `op-fork`: in cmux or not, and the result of each. The model checks the design at set points. It does not check a live run. The scripts of R5 check each run. Not chosen: it did not list the states, so the state check of R10 could not name them. It also left out the missing-fact and failed-command paths. R13 replaces it. Dropped 2026-10-18.
- **R12. Open VS Code at the root.** The user runs `op-code`. VS Code shows a window on the root of the git checkout that holds the session's directory. If a window on that folder is open already, VS Code brings it to the front. If the directory is not in a git repo, `op-code` opens nothing. If `code` fails, it says so and gives the command. Not chosen: The user runs `op-code` to see the diff, and VS Code's Source Control panel shows only uncommitted changes. R15 replaces it and adds the branch diff against `main`. Dropped 2026-10-18.
- **R10. Each run is checked by scripts.** The check scripts run after each run of a skill, on that run. A run passes only when each check of its skill passes. Not chosen: it did not say who starts the checks. R16 replaces it: the skill's script runs them as its last step and prints nothing on a pass, to keep the footprint of R14 small. Dropped 2026-10-18.
- **R9. Session facts.** Each skill finds the facts it needs about the session it runs in, without asking the user. `op-code` needed the directory, the root of its git checkout, and whether the session runs inside cmux. Not chosen: `op-code` no longer opens a cmux pane (R17), so it does not need the cmux fact. R18 replaces it. Dropped 2026-10-18.
- **R15. Open VS Code and the diff.** `op-code` shows a VS Code window on the git checkout root, and also shows the branch's whole diff against `main` in a cmux pane (`cmux diff --branch`). Not chosen: The user wants to see the changes inside VS Code only, not in cmux. R17 replaces it. Dropped 2026-10-18.
- **R16. Each run is checked by scripts.** The script of each skill runs its checks as its last step. The state check of `op-fork` reports the state the run is in, as named in the model of R13. Not chosen: the model of R13 is dropped, so the state check names its own end states. R19 replaces it. Dropped 2026-10-18.
- **R13. The model checks the design only.** A Quint model holds the states and moves of `op-fork`: facts found or missing, in cmux or not, a command failed or not, and the end state of each path. It checks the design, not a live run. Not chosen: The user dropped the model for now. The checks of R19 still check each run. Dropped 2026-10-18.
- **R19. Each run checks itself.** The script of each skill ends by checking what it did. The output check of `op-code` confirms the VS Code window, and a research line asked how a script sees which folder a window has open. Not chosen: `code` has no command that lists the open workspaces. The user agreed that the check of `op-code` confirms only that `code` ran on the right root without an error. R21 replaces it. Dropped 2026-10-18.
- **R17 for one day: a clean window.** The window shows no editor tab, and Source Control is the view in front. `op-code` asks the harness VS Code extension to do it, through a `vscode://` link with the folder in it. Not chosen: On 2026-10-21 each run came with a slow reload. VS Code's log shows a new window, `window2`, take over from `window1`, whose extension host then exited, with no app update. The link is the likely cause, not a proven one. The user would rather keep the tabs than wait for a reload. R17 is back to opening the window only.
- **R17. Open VS Code at the root.** The user runs `op-code` to see the session's work in VS Code. VS Code shows a window on the root of the git checkout that holds the session's directory. In a linked worktree that is the worktree root. In the main checkout it is the repo root. Not chosen: `! code .` does the same from the session's root, and Claude sessions stay at the root. The user ran it in a worktree on 2026-10-24, and VS Code opened the worktree window. The user removed `op-code` on 2026-10-24. Its output check moved to `op-kb-diff`, which used it too (R21, R22).
